# 03 · 分步演练指南

> 面向你本机环境（Dify 1.17.0 + Weaviate 1.27.0 + nginx `8080`）。共 6 个阶段，按顺序执行，约 2~3 小时可全部跑完。
> 约定：所有 `-ApiKey` 均为**数据集 API Key**（不是 App Key，也不是登录密码）；所有 `-AppKey` 为聊天助手应用的 API Key。

---

## 阶段 0 · 准备（10 分钟）

### 0.1 配置 Embedding 模型（若未配置）

1. 打开控制台 `http://localhost:8080` → 右上角头像 → **设置 → 模型供应商**；
2. 添加任意可用 Embedding 模型（你的 `OPENAI_API_BASE` 已指向兼容端点，可直接用它；若没有可用模型，先配置该供应商并填 Key）；
3. 验证：在「知识库」新建页面能看到 Embedding 模型下拉可选。

### 0.2 创建知识库并生成数据集 API Key

1. 控制台 → **知识库 → 创建知识库**：名称 `研发知识库演练`，索引方式选 **高质量**（High Quality），Embedding 模型选刚配置的；
2. 打开该知识库 → 右上角 **设置 → API 访问** → **创建 API Key** → 复制保存；
3. 记下知识库 ID（知识库列表 URL 中 `/datasets/<ID>` 或 API 返回）。

### 0.3 发布 Weaviate 端口到宿主机（不动你的 compose）

```powershell
cd C:\Users\001\dsh\dify-rag-lab
.\scripts\01-publish-weaviate-port.ps1
# 预期输出: Weaviate proxy started: http://127.0.0.1:8090
```

原理：加一个 `alpine/socat` 透明代理容器挂在 `docker_default` 网络，把 `weaviate:8080` 映射到宿主 `127.0.0.1:8090`，用于阶段 3/4 直查。**不修改、不重启任何 Dify 容器**。

### 0.4 设置演练参数（推荐用环境变量，脚本会自动读取）

```powershell
$env:DIFY_BASE_URL       = "http://localhost:8080"   # nginx 入口
$env:DIFY_DATASET_ID     = "<你的知识库ID>"
$env:DIFY_DATASET_API_KEY= "<阶段0.2生成的数据集API Key>"
$env:WEAVIATE_URL        = "http://localhost:8090"
```

## 阶段 2 · 三种检索方式对比（20 分钟）

**目的**：体会 `semantic_search` / `full_text_search` / `hybrid_search` 的差异与 score 口径。

```powershell
.\scripts\04-retrieve-compare.ps1 -Query "支付网关调用超时应该怎么办"
```

预期输出（每种方法 top 3）：

```
[hybrid_search]    top1 score=0.82  支付网关调用超时处理...
[hybrid_search]    top2 score=0.79  ...
[semantic_search]  top1 score=0.81  ...
[full_text_search] top1 score=13.4  ...   ← 注意：BM25 分数与语义分数量纲不同
```

要点：

- `semantic_search` 的 score = 1 − 余弦距离（≈[-1,1]）；`full_text_search` 是 BM25 原始分，**不可跨方法比较**；
- 混合检索 `weights.weight_type=semantic_first` 时以语义为主、关键词兜底；
- 试试 `-Query "JWT 过期了怎么刷新"`，观察关键词缺失时 full_text 的召回质量下降。

### 2.2 用评测集打分（hit@1 / hit@5）

语料自带的 14 条评测题（覆盖 8 份文档的关键事实）可以量化检索质量：

```powershell
.\scripts\04b-evaluate.ps1
# 输出逐题明细 + 汇总：hit@1 = x/14 (xx%)  hit@5 = y/14 (yy%)
```

预期：默认切分（500 token / 重叠 50）+ hybrid_search 下 hit@5 应 ≥ 12/14；hit@1 偏低是正常的（真实语料有主题重叠）。

调参实验（改完重跑评测集，量化对比）：

- `max_tokens` 200 vs 500：分段更碎 → 细粒度召回更好，但上下文可能断章取义；
- `chunk_overlap` 0 vs 50：重叠提升边界问题命中，代价是重复存储；
- 开启 Rerank（`reranking_enable: true` + 配置 rerank 模型）：top1 命中率通常明显上升。

这就是 docs/04 第 1 节"建立评测集"的最小落地版——先定基准，再调参，别拍脑袋。

## 阶段 4 · Java 服务（30 分钟）

**目的**：用 Spring Boot 把「Dify 检索」与「自实现检索」做成可对照的实验台。

### 4.1 编译并启动

本机无 JDK/Maven，用 Docker 编译（或直接 IDEA 打开 `backend/` 运行）：

```powershell
cd C:\Users\001\dsh\dify-rag-lab\backend
docker run --rm -v "${PWD}:/build" -w /build maven:3.9-eclipse-temurin-17 `
  mvn -q -DskipTests package
docker run -d --name dify-rag-lab --network docker_default `
  -e DIFY_BASE_URL=http://nginx:8080 -e WEAVIATE_URL=http://weaviate:8080 `
  -e DIFY_DATASET_API_KEY=<key> -p 8081:8081 dify-rag-lab:0.0.1
```

（本地有 JDK 的话直接 `mvn spring-boot:run` 即可，`application.yml` 已带默认值。）

### 4.2 体验接口

```powershell
# 1) Dify 检索
curl http://localhost:8081/api/rag/retrieve -H "Content-Type: application/json" `
  -d '{"query":"支付网关超时","search_method":"hybrid_search","top_k":3}'

# 2) 直查向量库（看 Dify 建的 collection）
curl http://localhost:8081/api/vdb/collections

# 3) 自实现向量检索（Java 自己调 Embedding + nearVector）
curl http://localhost:8081/api/vdb/collections/Vector_index_xxx_Node/search `
  -H "Content-Type: application/json" -d '{"query":"支付网关超时","top_k":3}'

# 4) 对照实验：同 query，Dify 结果 vs 自实现结果
curl http://localhost:8081/api/rag/compare?query=支付网关超时
```

### 4.3 关键源码导读（`backend/src/main/java/...`）

| 文件 | 学到什么 |
|---|---|
| `dify/DifyApiClient.java` | Dify Service API 的完整调用姿势（multipart、鉴权、轮询） |
| `weaviate/WeaviateClient.java` | Weaviate REST：schema、GraphQL nearVector / bm25、对象读写 |
| `embedding/EmbeddingClient.java` | OpenAI 兼容 `/embeddings` 调用——理解"向量从哪来" |
| `rag/RagService.java` | 自实现 semantic/hybrid 的加权融合公式（对照 Dify 的实现） |

## 阶段 5 · 问答应用 + 引用溯源（20 分钟）

**目的**：从"检索"升级到"问答"，验证端到端 RAG 效果。

1. Dify 控制台 → **创建空白应用 → 聊天助手**：名称 `研发问答助手`；
2. 左侧添加 **知识库** → 选择 `研发知识库演练`，检索方式选 **混合检索**；
3. 右上角 **发布** → **API 访问** → 复制 **App API Key**；
4. Java 网关直接代理：

```powershell
curl http://localhost:8081/api/rag/chat -H "Content-Type: application/json" `
  -d '{"query":"支付网关 3 次重试都失败怎么排查？","app_key":"<App API Key>"}'
```

预期返回：回答正文 + `records[]`（命中的 chunk 与 score）——这就是"引用溯源"。

调优实验：

- 检索方式改为 `semantic_search` / `full_text_search`，回答质量变化？
- `score_threshold` 从 0 提到 0.6，幻觉是否减少、漏召回是否增多？
- 加一个 Rerank 模型（如 bge-reranker），观察 top1 命中是否更稳。

## 附 · 常见报错速查

| 报错 | 原因与处理 |
|---|---|
| `provider_not_initialize` | Embedding 模型未配置 → 阶段 0.1 |
| `dataset not exist` | DatasetId 填错或用了 App Key → 核对阶段 0.2 |
| `indexing_technique is required` | 传文档时没带 `data` 里的 `indexing_technique`，且知识库未初始化 → 首次传文档必带 |
| 上传 413 | 文件超限（默认 15MB）→ 换小文件或调 `UPLOAD_FILE_SIZE_LIMIT` |
| 直查 weaviate 连不上 | 代理容器没起 → 跑 `01-publish-weaviate-port.ps1` |
| `Invalid doc_form` | doc_form 只能是 `text_model` / `hierarchical_model` / `qa_model` |

### C. 选语料的三个标准

1. **有结构**：清晰的标题层级（Markdown `##`/`###`），Dify 切分按结构更稳；
2. **有密度**：数值、名词、术语密集，否则检索"太容易命中"练不出调参手感；
3. **有交叉**：多份文档主题有重叠，才能暴露召回质量问题（正是 04b 评测集能打分的场景）。
