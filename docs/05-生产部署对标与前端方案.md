# 05 · 生产部署对标与前端方案

> 回答两个问题：① 当前「Java 网关 + Dify 都在 Docker」的环境对标生产 OK 吗？
> ② 前端怎么安排，也靠 Dify 提供的能力吗？

## 1. 当前环境画像（现状盘点）

```
┌─ 宿主机（单机 Docker Desktop）──────────────────────────────────┐
│  docker_default 网络                                            │
│  ┌─────────┐  ┌─────────┐  ┌──────────┐  ┌──────────────┐      │
│  │ Dify    │  │ Dify    │  │ Weaviate │  │ Java 网关    │      │
│  │ api/worker│ │ web(管理端)│  │ 1.27     │  │ (演练版)     │      │
│  └────┬────┘  └────┬────┘  └────┬─────┘  └──────┬───────┘      │
│       │  Postgres 15 / Redis 6（Dify 元数据）    │              │
│  nginx :8080/:443 ── 控制台与 Service API ──────┘              │
└─────────────────────────────────────────────────────────────────┘
前端：暂无（演练全部走 API/脚本）
```

**做对的地方**：组件齐全、Weaviate 不暴露公网（内网 + 127.0.0.1 代理）、数据面全部走 Service API、与 Dify 解耦（可替换）。

**对标生产的差距**：见下表。

## 2. 生产对标差距清单

| 维度 | 当前（演练） | 生产要求 | 改进动作 | 优先级 |
|---|---|---|---|---|
| 部署形态 | 单机 Docker Desktop | 多副本 / 托管 | api+worker ≥2 副本；Postgres/Redis 用独立实例或云托管（RDS/云 Redis）；网关前加 LB + TLS 终止 | P0 |
| 持久化 | compose volume（未逐一验证） | 明确的数据卷 + 备份 | 确认 weaviate/postgres/redis 的 volume 挂载；每日备份 + 季度恢复演练 | P0 |
| TLS/入口 | nginx 8080/443 裸 HTTP | 全链路 HTTPS | 443 上正式证书；控制台/API 仅内网或 VPN 可达 | P0 |
| 密钥 | `.env` 明文 + 固定 API Key | 密钥管理 + 轮换 | 密钥进 KMS/Vault；数据集 Key 按库隔离、定期轮换 | P0 |
| 网关鉴权 | 演练版无鉴权 | 网关层鉴权/限流/审计 | Java 网关接入 SSO/OAuth2；按调用方限流；写操作审计 | P1 |
| 可观测 | 无 | 日志/指标/链路/告警 | OTEL 接入；网关 QPS/P99/命中率指标；向量库与 Dify 监控 | P1 |
| 前端 | 无 | 见第 3 节 | 按形态决策树选型 | P1 |
| 容量成本 | 不评估 | 基线 + 增长规划 | docs/04 第 2/5 节清单 | P2 |

> 结论：当前环境**作为学习对标是合格的**（机制、API、网络隔离都验证了）；
> 要真正上线，先补 P0 四项，再补 P1。逐项动作与量化建议见 `docs/04`。

## 3. 前端方案：三种形态，按阶段选

Dify 提供的前端能力有两块：**管理端 Web（dify-web，只给管理员用，不能当终端用户界面）** 和 **WebApp 分享页（每个已发布应用自动生成，支持 iframe 嵌入）**。终端用户前端有三种形态：

| 形态 | 说明 | 优点 | 缺点 | 适用阶段 |
|---|---|---|---|---|
| **A. Dify WebApp / iframe** | 发布应用 → 用生成的 WebApp URL，或 iframe 嵌入企业门户 | 零前端开发，1 天可用 | 外观/权限受 Dify 限制；无法深度定制；终端用户直接触达 Dify | 起步/内部小范围试用 |
| **B. 自建前端 + Java 网关**（推荐生产） | Vue/React 前端 → 调 Java 网关 → 网关调 Dify Service API | 品牌/权限/工单联动自由；App Key 不暴露；网关统一鉴权限流审计缓存 | 需前端开发量 | 正式上线 |
| **C. IM 机器人**（钉钉/企微/飞书） | 网关封装 webhook 回调 → 调 Dify chat API | 用户在 IM 里直接用，落地最快 | 交互形态受限（卡片/富文本能力） | 与 B 并行 |

### 3.1 为什么"不全靠 Dify 的能力"？

- **安全**：App API Key 是数据面凭据，暴露给浏览器端 = 泄露面；自建前端经网关转发，Key 只在服务端。
- **鉴权**：Dify 的 Key 是"应用级"凭据，不是"用户级"；企业要按员工身份（SSO）控制谁能问、审计谁问了什么——这是网关的活。
- **聚合**：一个前端可能要编排多个 Dify 应用（知识库问答 + 工单 + 审批），还要做缓存、限流、结果增强（引用格式化、脱敏）——不适合让浏览器直连 Dify。
- **可演进**：将来换 RAG 后端（不用 Dify）时，前端/业务系统只依赖网关契约，不受影响。

### 3.2 推荐的最终形态（生产）

```
企业门户/IM ──► 自建前端(B) / IM机器人(C) ──► Java 网关 ──► Dify Service API ──► Weaviate / 模型
                    (Vue/React)            │鉴权/限流/审计/缓存/聚合│
                                           └──► 管理员用 Dify Web 管理知识库与应用
```

- **管理员**：Dify Web 控制台（管理知识库、编排应用、调参）——管理面保留 Dify；
- **终端用户**：自建前端 / IM 机器人，全部走网关，不接触 Dify；
- **Java 网关的职责边界**：做鉴权、限流、审计、缓存、多应用聚合、评估数据采集；**不做**切分、Embedding、向量检索（那是 Dify + 向量库的活，别重复造轮子）。

## 4. 对标生产的最小改造顺序（3 件事）

1. **补持久化与备份**：确认三个数据卷挂载（`docker inspect` 看 Mounts），配好每日备份（docs/04 第 3 节）；
2. **网关加鉴权**：Java 网关接入企业 SSO（OIDC），对外只暴露网关 8081，Dify 入口收进内网；
3. **前端选型落地**：先 A（WebApp/iframe）快速给用户用，同时启动 B（自建前端 + 网关）作为正式形态；IM 机器人按团队习惯并行接入。

> 顺序逻辑：先保数据（备份），再收紧入口（鉴权/网络），最后做体验（前端）——避免"体验先上线、数据没保障"。
