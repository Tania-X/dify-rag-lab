# 研发规范 · 代码质量与评审（示例文档）

> 演示语料：虚构公司"星云科技"研发中台知识库。内容贴近真实工程实践，用于 Dify 向量化演练。

## 1. 命名与结构

- 包名：全小写，反域名倒序（`com.xingyun.order`）；禁止用下划线。
- 类名：UpperCamelCase；方法名/变量名：lowerCamelCase；常量：全大写 + 下划线。
- 枚举统一用单数类名 + 常量成员；布尔变量用 `is/has/can` 前缀（如 `isPaid`）。
- 一个文件一个公开类；方法行数超过 80 行必须拆分；圈复杂度超过 15 必须重构。

## 2. 编码约束

- Java 版本基线：JDK 17，禁止使用已废弃 API（编译期 `-Xlint:deprecation` 视为错误）。
- 空值处理：方法入参一律 `@NonNull` / `@Nullable` 显式标注；禁止吞异常（`catch` 后必须 `log` 或抛出）。
- 集合操作：禁止在 `for-each` 中增删集合；优先使用 Stream + 不可变集合（`List.of` / `Map.copyOf`）。
- 并发：共享可变状态必须加锁或使用并发容器；禁止裸 `Thread`，统一走线程池，线程池必须命名。
- 配置：禁止硬编码；环境相关配置走 `application-{env}.yml` + 环境变量。

## 3. 测试要求

- 单元测试覆盖率：核心逻辑 ≥ 80%，整体 ≥ 60%（jacoco 门禁）。
- 新增代码必须带测试：分支覆盖 ≥ 70%；边界值（0、null、超大值）必须覆盖。
- 集成测试：涉及数据库/外部服务必须用 Testcontainers，禁止 mock 掉真实 SQL。
- CI 门禁：`mvn verify` 全绿 + 覆盖率达标 + 无 Snyk 高危漏洞，否则禁止合并。

## 4. Code Review 流程

- 所有变更走 PR：描述必须包含"变更原因 / 影响面 / 测试结果"三要素，缺一不可。
- 评审人：至少 1 名模块 owner + 1 名随机 reviewer（防熟人评审盲区）。
- 评审清单：并发安全、事务边界、异常处理、性能（N+1、大对象）、安全（注入/越权）。
- 时间要求：PR 发出后 4 个工作小时内完成首轮评审；超过 2 天无人评审自动升级到技术经理。
- 合并后 30 分钟内必须跑完 CI 全量流水线，失败立即回滚合并。

## 5. 技术债治理

- 每个 TODO/FIXME 必须挂工单，超过 2 个迭代未处理的计入技术债清单。
- 每月技术债盘点：按影响面（故障风险 × 修改频率）排序，Top10 进入下月迭代。
- 架构评审：任何跨模块的公共 API 变更，必须过架构评审会（每周四 16:00）。
